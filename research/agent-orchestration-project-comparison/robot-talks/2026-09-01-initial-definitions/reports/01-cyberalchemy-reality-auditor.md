## Key Findings

- **The objective is broader than the implemented product surface.** Cyberalchemy aims to preserve the chain from objective and authorization to action and evidence, but the proven operational baseline is currently a narrower set of repository-local orchestration components: a dispatch reader/control plane, append-only YAML ledger, agent-pool selector, operational skills and an opt-in SQLite ACI/APT pilot (`README.md:23-38`, `README.md:70-98`). The later comparison must not equate the whole objective with a delivered end-to-end system.
- **A substantial read and local-runtime substrate is built, while authoritative production execution is not.** The implementation map names working reader APIs, ten UIs, a governed SQLite runtime, a read-oriented Control Center and a separately bounded experimental runtime; the production runtime routes are mounted behind a closed gate (`implementations/README.md:53-65`, `implementations/server/main.py:41-76`). The local pilot is explicitly opt-in, loopback-only and preflight-gated (`implementations/README.md:67-84`). During this audit, the focused reader/confirm and ledger test scripts and the agent-pool smoke completed successfully; the confirm test itself checks marker creation, idempotence, traversal guards and absence of a ledger mutation (`implementations/tests/test_main.py:265-308`).
- **The implemented confirmation is a marker handoff, not autonomous dispatch.** `POST /api/confirm` validates a pending-sheet filename and writes `<sheet>.confirmed`; it neither appends a dispatch row nor launches an agent (`implementations/server/main.py:311-353`). The implementation documentation says the external orchestrator reaction remains separate work (`implementations/README.md:13-22`, `implementations/README.md:160-177`). A comparison should therefore distinguish UI confirmation, ledger registration, host launch and lifecycle closure instead of counting them as one capability.
- **Governed dispatch has concrete structural enforcement, but it is narrower than the governance thesis.** The appender validates schema/registry constraints, refuses a structurally corrupt ledger, appends idempotently and closes through a second append-only row (`.claude/skills/register-dispatch/SKILL.md:116-142`). Optional anti-bias mode enforces complete pairwise declarations when enabled, while some lifecycle rules—including approver membership—are explicitly outside appender enforcement (`.claude/skills/register-dispatch/SKILL.md:37-50`). This is evidence for bounded mechanics, not for the effectiveness of the decision-hygiene hypothesis.
- **The formal and decision-science claims remain candidates.** Noise aggregation, frame dispersion, anchoring freeze and fork detection are pending, and the repository says the anti-noise thesis has low veracity (`plans/governed-agent-work-infrastructure/PLAN.md:190-211`). The categorical interpretation is not typed in this repository and the core OBL-E3 obligation is explicitly open, with a named possibility that only the sequential fragment forms a category (`plans/governed-agent-work-infrastructure/PLAN.md:213-242`, `OBLIGATIONS.md:33-51`). These claims can be compared as research propositions, not credited as existing capabilities.

## Gaps or Inconsistencies

- The root README presents mandatory Agent hooks as denying launches when opening fails (`README.md:89-98`), but the current work-pack records a trusted Codex build that bypassed `PreToolUse` and prohibits code/review dispatch until reload plus live smoke evidence (`docs/features/agents-communication-infra/WORK-PACK.md:21-29`). The wrapper contract itself limits coverage to trusted, hook-capable local hosts and documents this exact bypass class (`docs/features/agent-provenance-telemetry/integration/stage-f/mandatory-host-wrapper.md:1-5`, `docs/features/agent-provenance-telemetry/integration/stage-f/mandatory-host-wrapper.md:99-112`). “Mandatory” is therefore conditional, not a repository-wide fact.
- The claimed sole-writer invariant has unresolved historical counterevidence. An audit found two close rows that could not have passed the validated appender and says the invariant remains promotion-blocked (`vault/audit/ledger-enum-drift-finding.md:35-63`). A later session reinterprets the drift as blocking a veracity label rather than an operation and explicitly questions the earlier “keystone” framing (`sessions/2026-07-22-1315-phase2-confirm-handoff.md:21-49`). The bypass evidence and its operational consequence must remain separate in synthesis.
- The root README is marked draft, private/unreviewed and lacks `LICENSE` and `CONTRIBUTING` (`README.md:1-18`). That weakens any inference that its current overview is a stable public product contract and leaves the repository's own redistribution/collaboration boundary unspecified for a study whose question includes code reuse.
- Passing focused local tests establishes behavior in this checkout, not production serving, provider execution, portability or live host interception. Those remain blocked or open in the current work-pack and Plan (`docs/features/agents-communication-infra/WORK-PACK.md:25-29`, `plans/governed-agent-work-infrastructure/PLAN.md:341-346`).

## Local Tensions

- **Two authorization paths coexist.** The designed confirm-gated path requires explicit human confirmation, while the host-hook path appends immediately before launch and has no separate human confirm (`README.md:163-185`). They share the ledger but do not embody the same human-authorization semantics; a project-level comparison that collapses both into “approval gates” will misstate the baseline.
- **Repository-local is an implementation boundary, not yet a settled product principle.** The current reader observes local filesystem state with near-zero target instrumentation (`README.md:62-64`), while the Plan still asks whether Codex and Claude adapters can reach equivalent operational states (`plans/governed-agent-work-infrastructure/PLAN.md:341-346`). The session assumption that Cyberalchemy “should remain repository-local” is therefore a proposition to test, not a confirmed constraint (`research/agent-orchestration-project-comparison/robot-talks/2026-09-01-initial-definitions/dialogue.md:34-41`).
- **Claim discipline is stronger than delivery breadth.** The repository deliberately exposes missing grounding and refuses to infer authority (`plans/governed-agent-work-infrastructure/essays/agent-language-system-view/essay.md:80-96`), yet several high-level differentiators—work language, recursive authority, category typing and the claim-to-refutation loop—remain proposal-only or unbuilt (`README.md:100-119`, `plans/governed-agent-work-infrastructure/PLAN.md:348-360`). This is a real governance property of the documentation, but not proof that the proposed runtime effects exist.
- **Local enforceability competes with host dependence.** Checked-in Claude and Codex hook configurations target launch and closure events (`.claude/settings.json:1-25`, `.codex/hooks.json:1-30`), but the enforcement boundary depends on host trust, hook loading and version behavior (`docs/features/agent-provenance-telemetry/integration/stage-f/mandatory-host-wrapper.md:99-112`). The architecture cannot yet claim host-independent governance.

## Questions for Synthesis

- Will the later study compare only operationally demonstrated capabilities, or also compare proposals? If both, what visible labels will prevent “built,” “local pilot,” “proposed,” “open” and “contested” from being merged?
- Which source governs current standing when the draft root README conflicts with a newer feature work-pack or session record?
- Is the comparison unit the reader/control plane, the dispatch lifecycle, the ACI/APT runtime, the broader knowledge-system thesis, or a deliberately separated set of these layers?
- What evidence threshold will make an external capability comparable to Cyberalchemy's baseline: source presence, automated tests, a live host smoke, or production use?
- Should repository-local operation be preserved as a constraint, or evaluated as one current deployment choice alongside provider-backed and distributed alternatives?
- How will the study represent the two dispatch paths and the unresolved sole-writer counterevidence without either erasing a working local mechanism or overstating end-to-end enforcement?
