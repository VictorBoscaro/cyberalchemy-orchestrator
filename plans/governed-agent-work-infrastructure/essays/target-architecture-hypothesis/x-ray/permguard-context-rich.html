Contextual architecture x-ray · claim ≤ proof

PermGuard decide o que pode atravessar a fronteira.

PermGuard é uma vertical de engenharia que conecta uma decisão de permissão formalizada em Lean a uma futura fronteira de execução. Ele ajuda a arquitetura geral a tornar autoridade operacional verificável e restritiva — mas não cria a autoridade, não prova segurança do agente e ainda não garante mediação inevitável no runtime.

1 · contexto e objetivo

O sistema precisa conectar intenção governada a efeitos sem confundir explicação com permissão.

O objetivo geral do ecossistema é manter trabalho ligado aos objetivos, decisões, suposições, ações e evidências que lhe dão sentido. O repositório de formalização fornece uma espinha Lean, um invariante por vez.

Objetivo

Qual resultado maior o trabalho deve servir?

Autoridade

Quem pode permitir qual efeito, sob qual escopo?

Execução

Qual tool call concreta está prestes a ocorrer?

Evidência

Qual decisão, policy, request e receipt permitem reconstrução?

PermGuard ocupa somente uma parte dessa cadeia. Ele responde se um request satisfaz políticas já fornecidas. Não decide se o objetivo é desejável, se quem forneceu a política tinha legitimidade, ou se a policy representa corretamente uma decisão humana.

Intenção governada

Objetivo, decisões, Task DAG, Dispatch, contexto e owners.

→

Permissão operacional

Policy estratificada + request estruturado + histórico opcional → allow/deny.

→

Efeito e receipt

Tool invocation somente após allow; resultado e decisão registrados.

2 · distinção obrigatória

Há dois artefatos chamados PermGuard, com standings diferentes.

O nome compartilhado não licencia transferência de garantias. O kernel prova propriedades sobre estruturas Lean; o runtime precisa entregar estruturas fiéis e tornar a decisão inevitável.

ObjetoLocalResponsabilidadeStandingNão prova
PermGuard kernel + CLI lean-engineer/ decidePolicy, teoremas, matchers estruturados, trace guard e executável Lean. LEAN BUILD PASS Mediação completa, fidelidade ambiental ou legitimidade da authority source.

Subset rule. “Kernel comprovado” não pode virar “sistema seguro”. As garantias transferem somente quando o request e a policy reais correspondem fielmente às estruturas verificadas e toda tool call passa pelo monitor.

3 · o gap que ele tenta fechar

Um reference monitor é tão forte quanto seu núcleo, sua inevitabilidade e sua fidelidade de entrada.

O kernel cobre o fator decisório. Os outros fatores pertencem ao trust border e à topologia real de execução.

força operacional ≈ núcleo verificado × sempre invocado × fidelidade de entrada

A expressão é um modelo explicativo do README, não uma métrica calibrada. Se qualquer fator efetivo for zero, a garantia não alcança o runtime.

4 · arquitetura interna

A decisão provada fica no centro; parsing e enforcement permanecem visíveis ao redor.

A CLI não reimplementa a lógica decisória. Ela constrói regras verificadas, chama o kernel e mapeia erros para exit code 2.

PEP / Recordplanejado

Policy parser

Converte efeitos e kinds declarativos em mkCanonRule, mkBashRule ou mkFetchRule. Rejeita policy vazia, campos ausentes e segmentos malformados.

Request parser

Produz StructuredArgs tipados: tool, path segmentado, command opcional, scheme e host labels. Erros nunca viram allow.

Decision core

Uma layer que proíbe vence. Sem proibição, toda layer precisa fornecer um permit correspondente. Abstention de qualquer layer resulta em deny.

Trace mode

Com secretSources e history, egressGuard nega um webFetch após read permitido de path marcado secret.

Explanation

Relata a primeira layer que proíbe, a primeira que não permite, ou o caso em que todas permitem. É explicação operacional, não proof object.

Exit contract

0 = allow, 1 = deny, 2 = parse/trust-border error. O runtime planejado não pode enfraquecer esse fail-closed.

Trust border isolado em PermGuard.lean

A decisão é verificada para as estruturas produzidas. A correspondência entre filesystem/URL/histórico reais e essas estruturas continua sendo uma obrigação externa. O parser foi hardened contra policy vazia, slash embutido, host label com ponto e inputs desconhecidos, mas não é um parser formalmente verificado.

O que existe, o que está ligado e o que ainda é somente roadmap.

6 · encaixe com a arquitetura geral

PermGuard é um kernel de domínio para permissão operacional, não o kernel global nem a authority source.

Ele pode ocupar uma parte concreta da fronteira entre Dispatch confirmado e efeito físico, desde que policies e capabilities cheguem de owners atribuíveis.

Strategy / Protocol

Definem trabalho e topologia. Não devem emitir grants apenas porque uma tarefa existe.

Compiler

Materializa o Dispatch e bindings efetivos. Pode preparar o request que será guardado, mas não inventa authority.

Identity

Pode fornecer IDs e signatures estáveis para tools, recursos, owners e policies. A semântica de permissão continua no domínio PermGuard.

Execution / Fabric

É o candidato natural para interposição: antes da chamada, apresenta policy, request e history ao PEP.

Record

Persiste policy/digest, request canônico, decisão, explanation, invocation e receipt. Não fabrica verdade nem autoridade.

ContextManifest

O agente pode ler uma authority claim sem receber uma capability. Context possession e effect permission permanecem separados.

D9 não desaparece. PermGuard avalia uma policy. Alguém ainda precisa ser owner da decisão que produz essa policy, estabelecer precedência entre layers e assinar a binding efetiva para o Dispatch. Um checker de autoridade não se torna a fonte da autoridade.

7 · como ele ajuda

PermGuard transforma parte da autoridade runtime em uma fronteira pequena, negativa e testável.

“Negativa” significa que seu poder seguro é principalmente restringir, vetar e falhar fechado — não descobrir intenção, classificar segredos ou conceder legitimidade.

Menos autoridade implícita

Uma task ou tool disponível não implica allow. Cada layer precisa permitir explicitamente.

Defesa em profundidade

User, project e org podem compor como interseção, sem uma layer ampliar as demais.

Fail-closed verificável

Input malformado sai como erro, não como decisão permissiva.

Residue visível

Matcher, parser, realpath, DNS, history e sink coverage aparecem como cláusulas assumidas.

Explicação atribuível

A layer que proibiu ou não permitiu pode ser ligada ao request e à policy version.

Confinement comprovado

Read/write/edit e fetch possuem propriedades específicas, não apenas uma decisão booleana genérica.

Counterexamples preservados

O bash bypass é mantido como prova de limite, em vez de ser escondido pelo roadmap.

Extração futura

O diretório está em staging para um repositório standalone planejado, sem alterar o standing atual.

8 · trust border e não-claims

A borda cresce conforme capabilities são ligadas.

O refinement fibre formaliza essa assimetria: mais rungs úteis implicam mais precondições ambientais que o kernel não prova.

Matcher paramétrico

Os teoremas centrais funcionam para qualquer Rule.applies. Isso prova o combinador, não a fidelidade de todo matcher.

Filesystem real

Realpath, symlink, TOCTOU e case-fold permanecem fora do modelo de listas segmentadas.

URL e DNS

Scheme/host labels são estruturados, mas parsing real, redirects e DNS rebinding permanecem externos.

Histórico confiável

Trace taint assume gravação fiel, ordenada e não bypassável.

Secret labels

Segredo é input de policy por path prefix. Classificação por conteúdo é explicitamente não coberta.

Bash egress

isEgress cobre webFetch; curl via bash é um hole provado.

Covert flows

Canais implícitos, timing e laundering por recursos não marcados não são certificados.

Complete mediation

Mesmo um hook implantado evidenciaria uma topologia; não provaria universalmente ausência de bypass.

Policy legitimacy

Uma policy bem formada pode ter owner inválido, precedência errada ou escopo não autorizado.

Collapse-test do programa. Se a integração apenas chamar o CLI fora do tool path, ou se requests reais puderem divergir das estruturas parseadas, as provas permanecem verdadeiras no Lean enquanto a contribuição operacional cai para zero.

9 · validação operacional

As provas precisam encontrar fixtures, mutations e receipts reais.

O build Lean atual passa; o regression harness do runtime continua sendo o primeiro componente planejado.

Golden allow

Todas as layers permitem o request, nenhuma proíbe, parser aceita e exit code é 0.

Forbid mutation

Adicionar um forbid aplicável em qualquer layer muda o resultado para deny.

Abstaining layer

Adicionar layer sem permit correspondente restringe o allow — diferença essencial do flattening.

Empty policy

O kernel tem identidade algébrica permissiva; a CLI rejeita policy vazia no border.

Traversal

Path com .. é normalizado e não deve escapar do prefixo concedido.

Malformed segmentation

Slash dentro de segmento ou ponto dentro de host label produz error/2.

Tainted web fetch

Read permitido de secret prefix seguido de webFetch resulta em deny.

Bash bypass witness

O mesmo trace seguido de bash/curl continua allowed pelo guard atual; o teste deve preservar esse limite.

Evidência executada nesta edição. lake build completou 941 jobs com sucesso em 2026-07-28. Os gates #print axioms expõem dependências como propext, Quot.sound e, em alguns teoremas, Classical.choice; isso não deve ser resumido como “axiom-free”.

10 · formalização matemática

A semântica é uma interseção de autoridade com refinamentos monotônicos.

As fórmulas abaixo descrevem o núcleo efetivamente modelado. Elas não formalizam a legitimidade da policy nem o enforcement físico.

10.1 Objetos fundamentais

Decision = { allow, deny }
Effect = { permit, forbid }

Rule(Req) = Effect × (Req → Bool)
Layer(Req) = List Rule(Req)
Policy(Req) = List Layer(Req)
Req
Tipo abstrato de request no kernel; a CLI instancia como StructuredArgs.
Rule.applies
Matcher executável. A semântica central é paramétrica nesse matcher.
Layer
Um conjunto de policy com permits e forbids.
Policy
Sequência de layers independentes, por exemplo user/project/org.

10.2 Semântica relacional

Forbids(L,r) ≜ ∃ q ∈ L, q.effect = forbid ∧ q.applies(r) = true

Permits(L,r) ≜ ∃ q ∈ L, q.effect = permit ∧ q.applies(r) = true

Satisfies(P,r) ≜
(∀ L ∈ P, ¬Forbids(L,r)) ∧
(∀ L ∈ P, Permits(L,r))

Duas condições independentes: nenhuma layer veta e toda layer concede. Ausência de veto não basta.

10.3 Correspondência executável

decidePolicy(P,r) = allow ↔ Satisfies(P,r)

Esse bicondicional é o centro da soundness/completeness: o boolean decision procedure concorda com a spec relacional.

Forbids(L,r) ∧ L ∈ P ⇒ decidePolicy(P,r) = deny

Deny precedence é não-bypassabilidade do combinador. Não prova que um matcher não pode ser evadido por uma representação malformada.

10.4 Álgebra de composição

allow ⊓ allow = allow
x ⊓ deny = deny = deny ⊓ x

decidePolicy(P ++ Q, r)
= decidePolicy(P,r) ⊓ decidePolicy(Q,r)

Allow(P ++ Q) = Allow(P) ∩ Allow(Q)

(Decision, ⊓, allow) é um monoide comutativo idempotente. Para request fixo, decidePolicy(-,r) preserva concatenação como meet.

decidePolicy([],r) = allow

A policy vazia é a identidade/top algébrica. Operacionalmente isso é fail-open; por isso o parser da CLI a rejeita sem alterar o teorema do kernel.

10.5 Restrição e confinement

decidePolicy(extra :: P, r) = allow
⇒ decidePolicy(P,r) = allow

decidePolicy(P ++ Q, r) = allow
⇒ decidePolicy(P,r) = allow ∧ decidePolicy(Q,r) = allow

Adicionar policy não pode ampliar o conjunto de requests permitidos.

canonRule(permit, tool, prefix/**).applies(req) = true
⇒ prefix ≤prefix normalize(req.path)

Os teoremas especializados instanciam essa forma para read, write e edit.

10.6 Taint e trace refinement

Taint = { clean ≤ secret }

traceTaint(S, []) = clean
traceTaint(S, e :: es) = traceTaint(S,es) ⊔ eventTaint(S,e)

egressGuard(S,P,h,r) =
deny, if traceTaint(S,h)=secret ∧ isEgress(r)
decidePolicy(P,r), otherwise
egressGuard(S,P,h,r) = allow
⇒ decidePolicy(P,r) = allow

O trace guard é um refinement: ele só remove allows. O resultado de exfiltration depende da lista assumida de sinks; atualmente bash não entra em isEgress.

10.7 Refinement fibre do trust border

Capability = Boolpath × Boolegress × Booltaint

c ≤ c′ ⇔ cada rung ativo em c também está ativo em c′

Assumed(c) = { a | clauseActive(c,a) }

c ≤ c′ ⇒ Assumed(c) ⊆ Assumed(c′)

Ao ligar mais capabilities, entram novas precondições: realpath/TOCTOU/case-fold; URL fidelity/DNS rebinding; trace fidelity/bash sink. Isso é um refinement-system fibre conhecido, não typed residue nem nova matemática.

10.8 Julgamentos de integração com a arquitetura

Γctx ; Γcap ⊢ request r : ToolEffect

PolicyOwned(owner,P) ∧ Bound(P,dispatchDigest)
∧ Canonicalizes(rawRequest,r)
∧ decidePolicy(P,r)=allow
∧ MediationInstalled(toolPath)
────────────────────────────────────────────
PermittedInvocation(dispatchDigest,r)

Este é um julgamento arquitetural proposto, não um teorema existente no repositório. Ele explicita que decidePolicy=allow é necessário, mas não suficiente.

AuthorityClaim ∈ Γctx ⇏ Capability ∈ Γcap

WellFormedPolicy(P) ⇏ LegitimateOwner(P)

decidePolicy(P,r)=allow ⇏ PhysicallyExecutedThroughGuard(r)

As três não-implicações preservam D9, a diferença entre contexto e capability, e a diferença entre checker acceptance e enforcement.
